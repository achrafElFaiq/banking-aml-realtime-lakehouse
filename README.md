# Banking AML Real-Time Lakehouse

A data platform for Anti-Money Laundering (AML/LCB-FT) compliance in French retail banking. Combines real-time fraud detection with batch regulatory reporting using a Lambda architecture (streaming + batch) and a Medallion data warehouse (Bronze, Silver, Gold), built entirely on synthetic data.



## The Problem

In retail banking, when a customer taps their card or sends a transfer, the transaction is recorded immediately in the bank's system as `PENDING`. But this live record is not always the final truth: amounts can change (tips, foreign exchange corrections), transactions can be cancelled, or payments can be blocked for fraud.

The official confirmation comes from settlement files sent by clearing networks (Visa, Mastercard, STET) 1 to 3 days later. These files carry the legally binding, auditable version of each transaction.

This creates a dilemma for the compliance team building dashboards and reports:

- **Using only settlements:** the dashboard is accurate but 2-3 days behind. A fraudster can drain an account on Monday and nobody sees it until Wednesday.

- **Using only live transactions:** the dashboard is real-time but unreliable. Cancelled, modified, or blocked transactions appear as if they actually happened.

- **Using both and merging them:** the dashboard shows live data today (with a "pending" label) and reconciled, confirmed data for previous days. The compliance team gets real-time visibility without sacrificing accuracy.

This project implements the third approach.


## The Solution

The platform runs two processing layers in parallel, following a Lambda architecture:

- **Layer 1 (Batch):** A daily ELT pipeline that extracts data from the production database and settlement files, loads it into a Bronze layer, and transforms it through Silver to Gold using dbt inside PostgreSQL.

- **Layer 2 (Streaming):** A real-time consumer that reads live transaction events from Redpanda (Kafka API), applies velocity-based fraud rules, and updates the transaction status directly in the production database.

Both layers feed into a Metabase dashboard where the compliance team monitors live alerts and reviews auditable historical reports.

### Layer 1: Batch Pipeline (ELT)

#### Extract

All data is synthetic, generated by Python scripts using Faker with French locale (`fr_FR`). Three source systems are simulated:

- **Customers:** 500 French bank customers with weighted risk tiers (70% LOW, 20% MEDIUM, 7% HIGH, 3% PEP), loaded once into the production database.
- **Transactions:** generated continuously by the streaming producer, written to `prod_source.transactions` with status `PENDING`.
- **Settlements:** a daily Parquet file containing transactions from 1-3 days ago, with status changed to `SETTLED` and occasional amount corrections (simulating clearing adjustments from Visa/STET).

#### Load

Data is loaded into the Bronze layer of the PostgreSQL warehouse:

- **Customers and transactions** are loaded by dbt models that run a raw `SELECT *` from `prod_source` into the `bronze` schema, adding an `ingested_at` timestamp. This creates an immutable copy, decoupled from the production database.
- **Settlements** cannot be loaded by dbt (dbt only reads from databases, not files). A Python loader script reads the Parquet files and inserts them into `bronze.raw_settlements`.

Both steps are orchestrated by an **Apache Airflow** DAG that runs daily: first the settlement loader, then `dbt run`, then `dbt snapshot`.

#### Transform

All transformations happen inside PostgreSQL using **dbt**, following the Medallion architecture:

**Bronze (raw):** Unmodified copies of source data. Safety net for replaying transformations if downstream logic changes.

**Silver (cleaned):** 
- European decimal amounts (`"4 500,00"`) cast to `DECIMAL(18,2)`
- `is_cross_border` flag derived from beneficiary IBAN prefix
- Transactions and settlements reconciled via `FULL OUTER JOIN` on `transaction_id`, with status priority logic: `BLOCKED` > `SETTLED` > `PENDING`

**Gold (business-ready):**
- `fct_transactions` - every reconciled transaction joined to customer risk tier
- `fct_daily_aml_alerts` - 30-day rolling cross-border sum per customer, flagging those exceeding the ACPR threshold of 10,000 EUR
- `snap_customers` - SCD Type 2 snapshot tracking changes to risk tier, address, and city over time (built with `dbt snapshot`)

### Layer 2: Streaming Pipeline

A Python producer simulates the bank's payment gateway. For every transaction, it simultaneously:
1. Writes a row to `prod_source.transactions` (status = `PENDING`)
2. Pushes a JSON event to a Redpanda topic

A Python consumer reads from that topic in real time and applies a velocity rule: if a `HIGH` or `PEP` risk customer makes 5 or more `INSTANT_SEPA` transfers within 60 minutes, the consumer updates the transaction directly in the production database:

```sql
UPDATE prod_source.transactions
SET status = 'BLOCKED', blocked_reason = 'VELOCITY_RULE: 6 INSTANT_SEPA in 42 min'
WHERE transaction_id = '...'
```

No separate alerts table. The transaction record itself carries the full lifecycle through its `status` and `blocked_reason` fields.

---

### Dashboard

Metabase connects to the PostgreSQL warehouse and serves two types of views:

- **Batch analytics** (from `gold` schema): transaction volume by status, AML alerts triggered by the 10,000 EUR/30-day rule, customer risk tier distribution, and PENDING-to-SETTLED conversion rates.
- **Near real-time monitoring** (from `prod_source`): live transaction feed, blocked transactions today, and velocity alert activity.

---

### Data Quality and CI/CD

The pipeline enforces data quality through **dbt tests** and **dbt-expectations** contracts: not-null checks, uniqueness constraints, accepted values for enums, and referential integrity between facts and dimensions.

A **GitHub Actions** CI/CD pipeline runs on every pull request: Ruff and mypy for Python linting, SQLFluff for SQL style, and `dbt build` (which runs both models and tests). Nothing merges red.

## Design Decisions

### Why a Rule Engine, Not ML

In AML/LCB-FT, the regulator (ACPR/Tracfin) requires detection logic to be explainable and auditable. A 10,000 EUR / 30-day rolling threshold must be justifiable line-by-line before a regulator. A black-box model cannot provide that traceability. The rule engine is a deliberate, regulation-driven choice, not a limitation. ML is reserved for alert prioritization (scoring), never for replacing auditable rules. This aligns with the EU AI Act's transparency requirements for high-risk systems.

### Why Lambda (Stream + Batch), Not Just One

Velocity fraud must be caught in seconds. The batch layer cannot do that. Cumulative 30-day thresholds need complete historical data. The stream cannot do that. Each path optimizes for a different constraint. Running both is the engineering cost of serving two incompatible latency requirements. A modern alternative (Kappa architecture, stream-only with replay) is noted in the roadmap as a potential evolution.

### Why Settlements and Transactions Are Separate Sources

Live transactions are provisional. Settlements are the legal truth. The Silver layer reconciles both via `FULL OUTER JOIN` on `transaction_id`, applying priority logic: `BLOCKED` > `SETTLED` > `PENDING`. This ensures dashboards show the most accurate available information at any point in time.

### Why HMAC-SHA256 for IBAN Pseudonymization

An IBAN has low entropy and an enumerable keyspace. A plain SHA-256 hash is reversible by brute force or rainbow tables. HMAC with a secret key defeats offline reversal. Under GDPR this remains pseudonymized personal data (still in scope), not anonymized data. This is the honest legal characterization.

### What Would Change in Production

- The real-time dashboard would read from a **read replica**, not the primary OLTP database
- Bronze would live on **object storage** (S3) rather than in Postgres, to separate compute from storage
- The streaming consumer would use **Spark Structured Streaming** or **Flink** for distributed, checkpointed windowing instead of in-memory Python dicts
- Settlement files would arrive via **SFTP** or a managed file transfer service, not generated locally
- Secrets (HMAC key, database credentials) would be managed by **AWS Secrets Manager** or HashiCorp Vault, not hardcoded
